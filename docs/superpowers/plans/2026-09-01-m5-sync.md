# M5 Comptes & Sync — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Comptes utilisateurs (Supabase), synchronisation du journal d'événements multi-appareils (conflict-free par construction), leaderboard rattaché au compte derrière l'interface existante, RGPD (export/suppression), et préparation de la publication Play Store — l'app restant STRICTEMENT identique à M4 quand aucun backend n'est configuré.

**Architecture:** Tout passe par une interface `SyncBackend` maison (TDD aux fakes) dont l'implémentation Supabase est une couche mince (supabase_flutter). Configuration par `--dart-define` (SUPABASE_URL/SUPABASE_ANON_KEY) : absentes → mode local pur (état M4, testé). Le journal d'événements M4 est l'unité de sync : push des événements locaux non-poussés, pull des événements distants inconnus, merge par id (les réducteurs dédupliquent déjà), recompute. Schéma SQL + RLS committés dans supabase/migrations avec un guide propriétaire de 5 minutes. Un checkpoint d'état borne le coût de replay (backlog M4). Le leaderboard Supabase implémente la MÊME interface Dart que drive.lmqc.fr (fallback conservé).

**Tech Stack:** supabase_flutter ; SQL (Postgres/RLS) ; Dart pur pour le moteur de sync ; share_plus (export).

## Global Constraints

- Base : master `v0.4.0-m5` — pardon: `v0.4.0-m4` (branche `m5-sync`). TDD ; CI 4 jobs verts par push (+ format gate) ; polling FOREGROUND ; gradle local impossible.
- **Sans configuration, rien ne change** : pas de réseau Supabase, pas d'UI compte visible (à part une tuile Réglages « Compte » à l'état « non configuré » discrète), tests d'identité M4 inchangés.
- Le journal reste la source de vérité locale ; la sync n'altère JAMAIS un événement existant (append-only des deux côtés) ; merge = union par event id ; l'ordre de replay local = ts croissant, puis précédence de type (les événements de gain — visite/xp — avant les événements de drain d'énergie à ts égal, table fixe documentée dans reducers), puis id (déterministe, documenté). [Amendé en revue T4 : le départage par id seul cassait le contrat verrouillé « xp avant drain » pour les événements intra-trajet à ts égal ; la précédence de type rétablit la sémantique en restant déterministe inter-appareils avec les seuls champs du schéma verrouillé.]
- Événements distants : mêmes types/schéma (contrat M4) ; les événements d'un AUTRE appareil du même compte sont fusionnés à l'identique.
- Secrets : jamais en repo ; --dart-define + guide ; anon key = publishable par design Supabase (RLS protège), documenter.
- RGPD : export = copie du journal (+ profil) en JSON partageable ; suppression = RPC serveur cascade + purge locale optionnelle ; textes français.
- Interfaces à ne pas casser : LeaderboardRepository, GameJournal/reduceAll, IdentityStore.

### Task 2c: QA propriétaire — l'onboarding doit S'ASSURER de « Autoriser tout le temps »
*(« quand tu demandes les permissions au debut, assure toi bien de la permission de location tout le temps »)*

L'onboarding (Task 2b) enchaîne ensureForTrip() mais ne vérifie pas le résultat pour la localisation en arrière-plan. Exigences :
1. Après le flux de permissions, l'onboarding RE-VÉRIFIE currentTrackingMode(). Si background → terminé. Sinon (refus, ou retour de openedSettings sans « tout le temps ») : étape d'insistance dédiée — explication courte de POURQUOI (l'itinéraire continue écran éteint / app fermée ; sans ça Android coupe le GPS), bouton principal « Ouvrir les réglages » (openSettings), bouton secondaire discret « Continuer sans » (mode dégradé, bannière existante continuera de le proposer). Au retour des réglages (lifecycle resumed), re-vérifier : si accordé → continuer automatiquement ; sinon rester sur l'étape (l'utilisateur peut re-tenter ou continuer sans).
2. Play-compliant : jamais bloquant — « Continuer sans » toujours accessible ; pas de boucle infinie ; l'étape n'apparaît qu'à l'onboarding (le comportement au premier trajet reste celui d'aujourd'hui).
3. Le flag onboarded_v1 n'est posé qu'après cette étape (comme avant : kill → re-montre).
4. Tests : coordinator inchangé ; widget tests — mode background → pas d'étape ; foregroundOnly → étape visible ; « Ouvrir les réglages » appelle openSettings ; resume avec background accordé → avance tout seul ; « Continuer sans » → carte ; textes FR, thème balisage, SafeArea.

### Task 2d: QA propriétaire — mode basse consommation (GPS en pause à l'arrêt)
*(« et fais un mode basse consommation - si le telephone ne bouge pas (api physical activity), mets en pause le gps »)*

Pendant un trajet actif, si l'appareil est immobile de façon soutenue, suspendre le flux GPS pour économiser la batterie, et le reprendre dès le mouvement. Exigences :
1. **Signal d'immobilité** : Activity Recognition Transition API (ACTIVITY_TRANSITION STILL enter/exit) via le canal Kotlin existant (RandomwalkPlugin ; permission ACTIVITY_RECOGNITION déjà dans le flux). Fallback si l'API n'est pas dispo sur l'appareil : compteur de pas (TYPE_STEP_COUNTER déjà exposé par DeviceChannel) — pas de delta de pas ET pas de déplacement GPS > seuil pendant la fenêtre = immobile.
2. **Politique (décisions pinnées)** : pause seulement après immobilité soutenue ≥ 3 min (un feu rouge ne doit JAMAIS suspendre) ; en navigation guidée active, seuil doublé (6 min) ; reprise IMMÉDIATE sur STILL-exit (et sur delta de pas en fallback) ; pendant la pause, un fix de sécurité isolé toutes les 3 min (garde-fou contre un STILL-exit raté) ; la notification du service indique l'état (« En pause — immobile » puis retour à l'affichage normal) ; l'enregistrement du trajet n'est pas terminé/altéré par la pause (aucun événement de fin, la trace reprend simplement).
3. **Périmètre** : uniquement le foreground service de tracking (app/lib/tracking/ + plugin Kotlin) ; AUCUN impact quand aucun trajet n'est actif (le service ne tourne déjà pas) ; le RouteFollower/nav tolère le trou de positions (vérifier : pas de recalcul intempestif déclenché par le silence GPS — gpsSilent existe déjà dans TripSnapshot, réutiliser cette machinerie si elle s'y prête).
4. **Tests** : politique en Dart pur (machine d'états immobile/actif : transitions, seuils 3/6 min, feu-rouge < 3 min ne pause pas, reprise immédiate, fix de sécurité cadencé) TDD aux fakes horloge/canaux ; le canal Kotlin reste mince (enregistrement/désenregistrement du transition listener + events vers Dart) ; QA device propriétaire pour la vraie conso (ajouter au qa-device-checklist).
