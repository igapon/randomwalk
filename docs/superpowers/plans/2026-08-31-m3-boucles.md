# M3 Boucles & Promenades — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Générer des itinéraires « promenade » : boucles A→A à distance approximative fixée, routes A→B à distance fixée, et les deux en **durée** fixée (via la vitesse historique de l'utilisateur) — 3 candidats scorés au choix, navigables immédiatement avec le turn-by-turn M2, 100 % hors-ligne.

**Architecture:** Un `LoopPlanner` pur Dart place k points intermédiaires sur un cercle autour du départ (azimuts semi-aléatoires seedés) ou sur une ellipse A/B, route à travers via le moteur embarqué (requête multi-locations Valhalla, waypoints `through`), mesure, ajuste le rayon par dichotomie (cible ±10 %), génère 3 candidats et les score (écart, segments répétés, agrément). La durée fixe se convertit en distance par un `SpeedHistoryStore` (EMA par profil alimenté par les sessions terminées). L'UI de planification gagne un sélecteur de mode et des cartes candidates ; le candidat choisi devient l'itinéraire planifié standard (pilule Démarrer, nav M2 inchangée).

**Tech Stack:** Dart pur (planner, scoring, vitesse) ; Valhalla multi-waypoints via le canal existant ; Flutter UI (thème balisage).

## Global Constraints

- Base : master au tag `v0.2.0-m2` (branche `m3-boucles`). Valhalla 3.6.2 inchangé.
- TDD systématique (planner avec routeur FAKE injecté — jamais le vrai moteur dans les tests unitaires) ; CI 4 jobs verts par tâche poussée (polling FOREGROUND uniquement, jamais de watch en arrière-plan) ; builds Gradle locaux impossibles.
- Spec §4.2/4.3 contraignant : k∈[2..4] waypoints ; rayon initial ≈ cible/(2π) pour une boucle ; dichotomie 2-4 itérations, cible ±10 % ; 3 candidats (jeux d'azimuts différents, graine aléatoire INJECTABLE — jamais Random() non seedé dans la logique) ; scoring = écart à la cible + taux de segments répétés + agrément ; échec propre : « meilleur candidat » présenté avec son écart réel (« 4,2 km trouvé pour 5 km demandé »), jamais d'échec sec. A→B distance fixe : waypoints sur l'ellipse de foyers A,B. Durée fixe : distance = durée × vitesse (EMA par profil, défauts 4,5 km/h marche / 16 km/h vélo avant historique).
- UX propriétaire : démarrage en une action préservé ; insets Android partout ; UI française ; thème balisage (les 3 candidats = jaune balisage pour le sélectionné, encre/hydro atténués pour les autres) ; code/commentaires/commits anglais (Conventional Commits).
- Interfaces M2 à ne pas casser : RouteResult/RoutePlanner/TripController/nav. La navigation d'une boucle = RouteResult standard, zéro changement nav.

### Task 1: Géométrie d'offsets (`geo_offsets.dart`, TDD pur)

**Files:** Create `app/lib/loop/geo_offsets.dart` + `app/test/loop/geo_offsets_test.dart`

**Interfaces (Produces):**
- `(double lat, double lon) destinationPoint(double lat, double lon, double bearingDeg, double distanceM)` — formule du point destination sur sphère (R=6371 km, cohérent avec metersBetween).
- `List<(double,double)> circleWaypoints({required double lat, required double lon, required double radiusM, required int count, required double startBearingDeg})` — `count` points également répartis en azimut à partir de `startBearingDeg`.
- `List<(double,double)> ellipseWaypoints({required (double,double) a, required (double,double) b, required double detourM, required int count, required bool mirrored})` — points sur le côté (ou le côté miroir) de l'ellipse de foyers A,B dont le demi-petit axe ≈ detourM.

Tests contraignants : destinationPoint round-trip avec metersBetween (aller 1 km au nord → metersBetween ≈ 1000 ± 1 m ; idem est à 46° lat) ; circleWaypoints à count=3 → azimuts espacés de 120° ; ellipseWaypoints symétrie miroir ; distances plausibles.

- [ ] TDD (RED → GREEN, flutter analyze 0), commit `feat(loop): spherical offset and waypoint geometry`.

### Task 5: LoopPlanner (cœur M3, TDD serré)

**Files:** Create `app/lib/loop/loop_planner.dart` + `app/test/loop/loop_planner_test.dart`

**Interfaces:**
- Consumes: Tasks 1/2/4 (geo_offsets, repeatedSegmentRatio, routeMulti via une fonction injectée `Future<RouteResult?> Function(List<(double,double)>)`).
- Produces (consommé par Task 6) :
  - `enum PlanKind { loop, toDestination }`
  - `class LoopRequest { final PlanKind kind; final (double,double) start; final (double,double)? end; final double targetKm; final RoutingProfile profile; final int seed; }`
  - `class LoopCandidate { final RouteResult route; final double gapRatio; final double repeatedRatio; final double score; }`
  - `class LoopPlanResult { final List<LoopCandidate> candidates; final bool targetMet; }` (targetMet=false ⇒ l'UI affiche l'écart réel)
  - `class LoopPlanner { LoopPlanner({required this.router, math.Random Function(int seed)? rng}); Future<LoopPlanResult> plan(LoopRequest request); }`

Algorithme contraignant :
1. k = 3 waypoints (boucle : cercle rayon r₀ = targetKm·1000/(2π) ; A→B : ellipse detour₀ dérivé du surplus cible vs distance directe).
2. Pour chaque candidat c ∈ {0,1,2} : azimut de départ = rng(seed+c).nextDouble()·360 ; boucle de dichotomie ≤ 4 itérations : router(start + waypoints + [start|end]) → si null (échec route) réduire r de 30 % et réessayer (≤ 2 fois) ; ajuster r par bisection classique sur la distance obtenue vs cible ; stop si |gap| ≤ 10 %.
3. Score = 0.6·|gapRatio| + 0.4·repeatedRatio (boucle) ; A→B : 0.7/0.3. Trier ; targetMet = meilleur |gapRatio| ≤ 0.10.
4. Jamais d'exception pour « pas trouvé » : s'il existe ≥ 1 route, retourner les candidats triés avec targetMet=false ; s'il n'y a AUCUNE route (router null partout) → `LoopPlanResult(candidates: [], targetMet: false)`.

Tests (routeur fake dont la distance ≈ périmètre du polygone des locations — pur calcul) : convergence ±10 % pour 5 km marche ; candidats distincts (seeds) ; déterminisme à seed fixe ; A→B ellipse converge ; router-null partout → liste vide sans throw ; targetMet=false quand la cible est physiquement inatteignable (fake plafonné) avec le meilleur écart réel retourné ; dichotomie ≤ 4 appels routeur par candidat (compteur).

- [ ] TDD, commit `feat(loop): loop planner with bisection and candidate scoring`.
